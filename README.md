## Understanding the Issue

### Problem Description

The nous-core provider system has implementations for Anthropic, OpenAI, and Ollama, but no adapter for llama.cpp server. Users running llama.cpp locally have no way to connect it to the framework.

### Expected Behavior

A certified provider leaf should exist under `providers/llama-cpp/` implementing the provider-leaf contract (`ProviderDefinitionLeaf`, factory, adapter, index), allowing the framework to send inference requests to a locally running llama.cpp server (default `http://localhost:8080`) without requiring an API key.

### Current Behavior

No llama.cpp provider leaf exists. The providers directory only contains `anthropic/`, `ollama/`, and `openai/`. There is no llama.cpp entry in the auto-generated provider catalogs.

### Affected Components

- `self/subcortex/providers/src/providers/llama-cpp/` — new provider leaf directory
- `self/subcortex/providers/src/provider-definitions.ts` — auto-generated catalog (regenerated by script)
- `self/subcortex/providers/src/provider-adapters.ts` — auto-generated catalog (regenerated by script)
- `self/subcortex/providers/src/provider-factories.ts` — auto-generated catalog (regenerated by script)
- `self/subcortex/providers/src/__tests__/` — 5 existing test files updated to include the new vendor

## Solution Approach

### Analysis

The root cause is a gap in coverage: the provider system is built to be extensible (each provider is a "leaf" directory under `providers/` discovered by the codegen script), but no one has yet implemented the llama.cpp entry. There is no bug — the adapter just doesn't exist yet.

The maintainer confirmed in issue comments that this should be implemented as a certified provider leaf against the shared `ChatCompletionsProvider` primitive (the OpenAI-compat protocol layer), not as a fully custom provider like Ollama. The key differences from other providers are: local endpoint, no API key required.

### Proposed Solution

Create a `providers/llama-cpp/` leaf with the 4 required files (`definition.ts`, `adapter.ts`, `provider.ts`, `index.ts`), regenerate the provider catalogs via the existing codegen script, and add unit tests covering definition metadata, no-auth construction, invoke happy/error paths, stream chunk yielding, abort handling, and endpoint URL verification.

### Implementation Plan

Using UMPIRE framework (adapted):

**Understand:** The provider-leaf contract requires exactly 4 files: `definition.ts` (exports `providerDefinition` satisfying `ProviderDefinitionLeaf`), `adapter.ts` (exports `providerAdapter`), `provider.ts` (exports `providerFactory` satisfying `ProviderFactoryModule`), and `index.ts` (barrel). The codegen script auto-discovers these and regenerates the three catalog files.

**Match:** `providers/ollama/` is the closest model — it's also a local, no-auth provider. However, Ollama has a custom wire format and its own `OllamaProvider`. llama.cpp speaks the OpenAI-compat format, so `adapter.ts` and `provider.ts` delegate entirely to `protocols/openai-api/`.

**Plan:**
1. Create `providers/llama-cpp/definition.ts` — `LLAMA_CPP_PROVIDER_DEFINITION` with `vendorKey: 'llama-cpp'`, `defaultEndpoint: 'http://localhost:8080'`, `auth.required: false`, `protocol: 'chat-completions'`
2. Create `providers/llama-cpp/adapter.ts` — re-export `chatCompletionsAdapter` from `protocols/openai-api/adapter.js`
3. Create `providers/llama-cpp/provider.ts` — factory that constructs `ChatCompletionsProvider` with `apiKey: 'no-auth'` fallback (bypasses the key guard; llama.cpp ignores the Authorization header)
4. Create `providers/llama-cpp/index.ts` — barrel exporting all three
5. Run `pnpm --filter @nous/subcortex-providers run generate:providers` to regenerate the catalogs
6. Update 5 existing test files that snapshot the full vendor roster to include `'llama-cpp'`
7. Add `__tests__/llama-cpp-provider.test.ts` with 13 tests

## Learnings & Reflections

### Technical Skills Gained

- **Provider leaf pattern in monorepos:** learned how a codegen script can auto-discover a directory structure and produce typed aggregate files — meaning contributors only write the leaf, never the registry wiring.
- **TypeScript `satisfies` operator:** used it to get compile-time contract checking on `as const` objects without widening the type. Also learned the edge case where `satisfies` doesn't propagate optionality into method signatures — had to explicitly annotate `options?: ProviderFactoryCreateOptions`.

### Challenges Overcome

- **Upstream rebase mid-implementation:** the maintainer pushed breaking changes to the base branch while I was working. Had to `git fetch upstream` and rebase, then update the definition to use the new `ProviderDefinitionLeaf` type and remove the hand-authored `wellKnownProviderId`.
- **TypeScript optional parameter inference gap:** `satisfies ProviderFactoryModule` didn't propagate the optional `options` parameter into the concrete method signature — TypeScript still inferred it as required. Fixed by explicitly typing the parameter.
- **`npm` vs `pnpm`:** the repo uses pnpm workspaces. `npm install` fails with `EBADPLATFORM` errors. This was the first blocker and was resolved by switching to `pnpm`.

### What I'd Do Differently Next Time

- Read the contributing docs more carefully before starting — the provider-leaf pattern and the "what not to edit" guardrails were documented, but I initially planned around an `implementation.ts` approach before discovering the 4-file leaf contract.
- Check for recent upstream commits before starting implementation to avoid mid-work rebases.
